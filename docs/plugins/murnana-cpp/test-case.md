# C++ のテストケース作成

C++ のプログラムに対して、テスト(動きを確かめるためのプログラム)を書いたり、いまあるテストを見直したりする機能です。

## 話しかけ方

- 「この関数のテストを書いて」
- 「境界値のテストケースを追加して」
- 「TDD でこの機能を作りたい」
- 「リファクタリングの前に、いまの動きをテストで固定して」
- `/murnana-cpp:test-case 対象のファイルや関数`

C++ のテストを書きたいと話しかければ、この機能が自動で動きます。

## 何をするか

テストは「このプログラムが何をするべきか」を書く場所だという考え方で進めます。手順は、Kent Beck さんの「Canon TDD」(和田卓人さんによる日本語訳「テスト駆動開発の定義」)に沿っています。

1. **テストリストを先に書く。** いきなりテストを書かず、確かめたい動きを 1 行ずつ並べます。それぞれに「期待する結果がどこに書いてあるか」(説明書き、仕様、依頼の内容など)を添えます。
2. **リストから少しずつテストにする。** 全部を一度にテストにはしません。1 つ書いて動かすことで分かったことを、次のテストに生かすためです。
3. **書いたテストが失敗するところを一度見る。** 一度も失敗したことのないテストは、本当に間違いを見つけられるか分かりません。
4. **全体を動かして確かめ、報告する。**

進め方は、状況に合わせて 3 つあります。

| 進め方 | どんなとき | 変えるもの |
|---|---|---|
| A. テストを先に書く | まだない機能を作る、TDD で進めたい、不具合を直したい | テスト。頼まれたときだけプログラム本体も |
| B. あとからテストを書く | プログラムがすでにあり、仕様が分かる(迷ったときはこれ) | テストだけ |
| C. いまの動きを固定する | 仕様が分からない古いプログラムを、直す前に守りたい | テストだけ |

守っていること:

- **動きを確かめ、作りは確かめません。** 外から見える結果(返ってくる値、起きるエラーなど)だけを確かめます。中の作りに頼ったテストは、動きを変えない書き直しでも壊れてしまうからです。
- **期待する値は仕様から決めます。** プログラムを動かして出てきた値をそのまま正解にはしません(進め方 C だけは別で、その場合は「いまの動きを固定したテスト」だと分かるようにします)。
- **テストを通すためにテストを曲げません。** 確認を消す、正解をゆるめる、テストを飛ばす印を付ける、といったことはしません。
- **テストの中に判断を書きません。** 条件分けや繰り返しはテストに入れず、値の組み合わせは「パラメーター化テスト」という形にします。
- **テストの名前で動きが分かるようにします。** 「どんなときに、どうなるか」を名前に入れます。
- **時刻や乱数、通信に頼りません。** いつ、どの順番で動かしても同じ結果になるテストにします。
- **道具を勝手に入れません。** GoogleTest、Catch2 などのうち、プロジェクトがすでに使っているものに合わせます。足りないものがあれば、テストは書いたうえで「動かしていない」と報告します。

言語ごとの決まり(置き場所、名前の付け方、動かし方)は、スキル本体の「C++ specifics」にまとめています。テストケースの探し方と、よくない書き方の一覧は `skills/test-case/references/test-design.md` にあります。

## 聞かれること

- **期待する結果**: 仕様がどこにも書かれていない動きがあるときに聞かれます。
- **不具合の疑い**: 仕様どおりに書いたテストが、いまのプログラムで失敗したときに聞かれます。「プログラムの不具合」「いまの動きが仕様」「このテストは書かない」から選びます。

質問できない使い方(自動で動かすときなど)では、推測で進めず、その動きはテストにしないで報告にまとめます。不具合の疑いがあるテストはファイルから外し、報告に全文を載せます。

## 終わったあとの報告

- 選んだ進め方と前提
- テストリスト(テストにしなかった行と、その理由を含む)
- 書いたテストの一覧
- それぞれのテストが失敗するところを、どう確かめたか
- 見つかった問題(不具合の疑い、仕様があいまいなところ)
- 提案したけれど行っていない変更(テストしやすくするための、プログラム本体の直し方など)
- 動かしたコマンドと結果(動かせなかったときは「未実行」)

記録(コミット)は、頼まれたときだけ行います。

## 設計

### 手順を Canon TDD に合わせた理由

AI にテストを頼むと、プログラムを読んで、その作りをなぞったテストを一度にたくさん書きがちです。そうしたテストは、プログラムの間違いまで「正解」として写し取ってしまいます。Canon TDD が挙げている失敗(確認のないテスト、リスト全部を一度にテストにする、出てきた値を正解に写す、書き直しと混ぜる)を、そのまま守るべき決まりにしました。

### あとから書くテストでも「失敗」を見る理由

テストを先に書くと、機能がまだないので自然に失敗を見られます。あとから書くテストは最初から通ってしまうので、正解の値をわざと間違えて動かし、失敗することを確かめてから元に戻します。プログラム本体を壊して確かめる方法は、戻し忘れると危ないので取りません。

### プログラム本体を変えない理由

テストを書くつもりで頼んだのに、本体が書き換わっていると困ります。テストしにくいところは、直し方を提案するだけにしています。本体を変えるのは、機能の実装や不具合の修正を頼まれたときだけです。

### モデルを固定しない理由

テストケースを選ぶのは判断の多い仕事なので、いま使っているモデルのまま動かします。そのうえで、Sonnet でも手順を飛ばさないように、手順には番号を付け、動かすコマンド、結果の読み方、結果ごとの次の行動を表にして書いています。

### あらかじめ許可しているコマンド

テストを動かすコマンド(`ctest`、`cmake --build`)と、変更を確かめる `git status`、`git diff` だけを、確認なしで動かせるようにしています。道具を入れるコマンドや、記録(コミット)は許可していません。

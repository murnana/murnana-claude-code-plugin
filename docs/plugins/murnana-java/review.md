# Java のコードレビュー（review スキル）

Java のプログラムを Claude に読んでもらい、直したほうがよいところを報告してもらう機能です。見つけるだけで、プログラムは書きかえません。

## 使い方

「この変更をレビューして」のように頼むと、Claude が必要に応じてこの機能を使います。自分で呼ぶときは、次のように入力します。

```
/murnana-java:review                      まだコミットしていない変更を見る
/murnana-java:review src/                 フォルダーやファイルを指定して見る
/murnana-java:review main...HEAD          ブランチで変えたところを見る
```

何も指定せず、変更も見つからないときは、どこを見るかを質問します。

会話の流れに左右されない、別の目での確認がほしいときは、同じ基準で動くサブエージェント [code-reviewer](code-reviewer.md) を使ってください。

## 何を見るか

次の順に確かめます。基準の本文は、スキルのファイル（`skills/review/SKILL.md`）にあります。

| 順番 | 見るところ | 基準 |
|---|---|---|
| 1 | メモリーやファイルなどの片づけ忘れ（メモリーリーク・リソースリーク） | スキルの点検表。頼まれた内容にかかわらず、必ず確かめる |
| 2 | 動きの誤りと、Java でつまずきやすい書き方 | スキルの点検表 |
| 3 | プロジェクトの決まりへの違反 | プロジェクトの決まり |
| 4 | 名前の付け方 | プロジェクトの決まり。なければ、下の既定 |

### プロジェクトの決まりを先に使う

`CLAUDE.md`、`AGENTS.md`、`.claude/rules/`、`CONTRIBUTING.md`、`docs/` のスタイルガイド、それに点検用の道具の設定ファイルを探し、見つかった決まりを基準にします。文章で書かれた決まりを、設定ファイルよりも優先します。

### 名前の付け方の既定

プロジェクトに名前の決まりがないときは、次の書き方を基準にします。

- Oracle の「Code Conventions for the Java Programming Language」第 9 章と、Java 言語仕様（JLS）6.1 節（クラスは `UpperCamelCase`、メソッドと変数は `lowerCamelCase`、定数は `UPPER_SNAKE_CASE`、パッケージはすべて小文字）

Java を作っている Oracle（もとは Sun Microsystems）が公開している書き方です。古い文書ですが、命名の部分はいまも Java の標準ライブラリーと同じです。

決まりがなく、ファイル全体が別の書き方でそろっているときは、名前を 1 つずつ挙げず、「決まりが見つからず、このファイルは別の書き方でそろっている」という 1 件の指摘にまとめます。

## 報告の形式

```
結果: High <件数> / Medium <件数> / Low <件数>(対象: <見たファイルや範囲>)

## 使用した基準
## 指摘
## 確認できなかった点・前提
## 検証方法
```

指摘には、重大度（High / Medium / Low）と確かさ（Confirmed / Suspected）を別々に付け、場所（`ファイル:行`）、どうなると問題が起きるか、基準、最小の直し方を書きます。片づけ忘れの指摘には、確かめるための道具も添えます。

## 設計

### 読むだけにした

`allowed-tools` は `Read`、`Grep`、`Glob`、`LSP`、`AskUserQuestion` と、読み取りだけの `git status` / `git diff` / `git log` / `git show` に絞っています。レビューの途中でプログラムが変わると、どこまでが元の内容か分からなくなるためです。直すのは、報告を読んだあなたが頼んだ指摘だけです。ビルドや点検用の道具も動かしません。動かし方はプロジェクトごとに違い、事前に許可する範囲が広がりすぎるためです。

### 片づけ忘れを必ず確かめる

メモリーリークは、動かしてもすぐには気づけず、長く動かしてから問題になります。そのため「名前だけ見て」と頼まれたときでも、片づけ忘れの確認は省きません。確保した場所を先にすべて書き出し、正常に終わる道、途中で戻る道、エラーの道のそれぞれで片づけているかを追います。

### 根拠のない指摘をしない

指摘には、場所と、問題が起きる道すじを必ず書きます。読めなかった部分に左右されるものは Suspected とし、何を見れば確かめられるかを書きます。指摘がなければ「なし」と報告します。

### 名前だけの依頼でも使われるようにした

スキルの `description` に、名前だけの確認や、貼り付けたコードも対象だと書いています。最初の説明文では、「名前の付け方を見て」という依頼で Claude がこのスキルを使わず、C++ では開発元の書き方ではない別の書き方で答えたためです（eval の `review-naming-default` で確認）。

### モデルを固定しない

`model` は指定せず、会話で使っているモデルのまま動きます。レビューは判断の重い作業なので、軽いモデルに固定しないためです。Sonnet でも同じ形の報告になるように、手順は番号付きにし、使うコマンドと報告の見出しを固定しています。

### スキルとサブエージェントで基準を共有する

基準と手順は、このスキルにだけ書いています。サブエージェント [code-reviewer](code-reviewer.md) は、起動するときにこのスキルを読み込みます。同じ内容を 2 か所に書くと、片方だけ直して食い違うためです。

# Python のコメント作成

Python のプログラムを読んで、コメント(プログラムの中に書く説明文)や使い方の説明(docstring)を書いたり、いらないコメントを整理したりする機能です。

## 話しかけ方

- 「Pythonのコメントを書いて」
- 「この関数にdocstringを付けて」
- 「なぜこう書いたのかコメントで説明して」
- 「不要なコメントを整理して」
- `/murnana-python:comment 対象のファイル`

Python のプログラムに説明を付けたいと話しかければ、「コメント」や「docstring」という言葉を使わなくても、この機能が自動で動きます。

## 何をするか

情報ごとに、書くのにふさわしい場所があるという考え方で整理します。

| 書きたいこと | 置き場所 |
|---|---|
| どう動くか | プログラムそのもの(分かりやすい名前にする) |
| 何をするべきか | テスト(動きを確かめるためのプログラム) |
| なぜ変えたか | コミットメッセージ(変更を記録するときの説明) |
| なぜほかのやり方にしなかったか(あえてやらなかったこと) | コメント |
| 使う人との約束(渡す値、返ってくる値、起きうるエラー) | 使い方の説明(docstring) |

そのうえで、次のことをします。

- プログラムを言い換えただけのコメントや、使われていない古いプログラムを残したコメントは消します。
- 「いつ何を直したか」という経緯のコメントは消して、コミットメッセージの案として報告に書きます。
- 使う人が頼りにする動き(「見つからないときは何も返さない」など)を書いたコメントは、使い方の説明(docstring)に移します。
- ほかの人が使う部品には、使い方の説明(docstring)を付けます。書き方はプロジェクトの決まりに合わせ、決まりがないときは Google の形にします。
- 「なぜほかのやり方にしなかったか」は、選ばなかったやり方とその理由を、対象の行のすぐ上にコメントとして書きます。

プログラムそのもの(コメントと使い方の説明以外の部分)は書き換えません。書き換えていないことは、作業の前後を比べて機械的に確かめます。名前の付け直し、部品の切り出し、テストの追加などは、報告で提案するだけです。

著作権の表示、ほかの道具への指示が書かれたコメント(型の検査や書式の検査を止める指示など)は、そのまま残します。「あとでやること」(TODO)のコメントも消しません。

## 聞かれること

- **理由**: わざとそう書いたように見えるのに、理由が会話からも設定からも変更の記録からも分からない場所があるときに聞かれます。
- **あとでやること(TODO)**: 担当者や課題の番号、いつやるかの条件が書かれていないときに聞かれます。

質問できない使い方(自動で動かすときなど)では、推測で理由を書くことはせず、その場所と聞きたいことを報告にまとめます。コメントの言語は、プログラムのほかのコメントに合わせます。コメントがひとつもないときは英語で書きます。

## 終わったあとの報告

- 消したコメント、移したコメント、書き足したコメントの一覧(使い方の説明を付けた・直した部品を含む)
- 提案したけれど行っていない、名前の付け直しやテストの追加
- 「なぜ変えたか」を書いたコミットメッセージの案
- 理由が分からず書かなかった場所と、聞きたいこと
- プログラムそのものを書き換えていないことと、説明の書き方を確かめた結果

記録(コミット)は、頼まれたときだけ行います。

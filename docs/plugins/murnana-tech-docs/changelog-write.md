# changelog-write スキル

`/murnana-tech-docs:changelog-write` — CHANGELOG.md を [Keep a Changelog](https://keepachangelog.com/) に沿って作成・追記する。頼まれたときだけバージョンを切る。

## 使い方

- 起動は**明示的なスラッシュコマンドのみ**（`disable-model-invocation: true`）。
- `$ARGUMENTS` に記録したい変更のヒントを渡せる。「release」「バージョンを切って」「1.2.0 にして」のようにバージョンを指定すると、リリース切りまで行う。
- 書き込む前に、必ず追記内容を提示して承認を待つ。コミットはしない。

| Step | やること |
|---|---|
| 1 | 対象の CHANGELOG を決める（モノレポでは変更パスに対応するもの） |
| 2 | プロジェクト規約を探す（見つかればそれが最優先） |
| 3 | 新規作成のとき: Keep a Changelog の最新版を確認し、言語（既定は会話の言語）とバージョニング方式を決める |
| 4 | 既存ファイルのとき: 前文の版・言語・カテゴリ順・リンク形式をそのまま引き継ぐ |
| 5 | 前回リリースからの変更と、その元になった Issue / PR を集める |
| 6 | 書き方ルールに沿ってエントリを起草する。動作として書けない変更は相談する |
| 7 | 提示して**承認を待つ** → 書き込む |
| 8 | 頼まれたときだけ: バージョン番号を決め、`[Unreleased]` を `[x.y.z] - YYYY-MM-DD` に移し、リンクを更新する |

## エントリの書き方ルール

詳細と日英の例は [`references/entry-writing.md`](../../../plugins/murnana-tech-docs/skills/changelog-write/references/entry-writing.md) を正とする。要点:

- API の名前ではなく、何ができるようになったか、どんな現象が直ったかを書く
  - ただし、フラグ・設定キー・環境変数など、ユーザーが自分で入力するものは名前を書いてよい。何ができるのかも併せて書く
- 過去形で書く
- 小さな変更も書く。設定・依存・動作環境の下限の変更も含める。動作として説明できないものは相談する
- 元になった Issue / PR / チケットの URL を、エントリ末尾にインラインで書く。ブランチではなく恒久的な URL を使う
- 不具合修正には、どの手順で起きた不具合かを書く。長くなったら「発生条件」と「症状」の 2 文に分ける
- 例外として、Deprecated と Removed には API 名を書き、移行先があればそれも書く。移行先がないときは「移行先はない」と書く
- 破壊的変更はコミットメッセージや版番号に頼らず diff から探し、ユーザーが取るべき対応を添える
- エントリの書き出しは、ユーザーが知っている機能名や領域名にする。カテゴリ内は影響の大きい順に並べる
- 「改善した」「軽微な修正」のような中身のないエントリは書かない

## 設計判断とその理由

- **なぜ明示起動のみか** — CHANGELOG はユーザーが読む公開文書で、いつ書くかは人間が決めたい。自動起動にすると、無関係な作業中に追記を提案してくるおそれがある。
- **なぜ Keep a Changelog の最新版を毎回取得するか** — 「新規作成時は常に最新版で書き始める」という要件のため。仕様は更新され続けており、作成時点（2026-10）でも 1.1.0 から 2.0.0（2026-06-07 公開）に上がっている。取得に失敗したときは、references にある 2.0.0 のスナップショットを使い、その旨をユーザーに伝える。
- **なぜタグから版を判定しないか** — 上流リポジトリのタグは仕様の版に追いついていない。2.0.0 公開後も最新タグは `v1.1.2` のままだった。そこで、keepachangelog.com 自身の `CHANGELOG.md` の最新見出しで判定する。仕様本文はレンダリング済みのページではなく、`source/en/<版>/index.html.md` の原文を読む。
- **なぜ既存ファイルの版を勝手に上げないか** — 2.0.0 自身が「従っている版にリンクを固定せよ」「新しい版を採用しても過去の履歴は書き直さない」としているため。古い版を使っているときは一言伝えるだけにして、判断はユーザーに任せる。
- **なぜ URL を必須にしたか（2.0.0 は任意としている）** — 2.0.0 はリンク切れやホスト依存を理由に、Issue / PR のリンクを任意とし、参照形式のリンクを勧めている。それでも、変更の経緯をたどれることを優先して必須にした。形式はエントリ末尾のインラインリンクにした。エントリだけ読めば参照先が分かるため。
- **なぜリリース切りを頼まれたときだけにしたか** — バージョン番号の決定はリリース計画に関わる判断で、追記のついでに行うものではないため。`plugin.json` や `package.json` などの版番号には触れず、変更が必要なファイルを伝えるだけにしている。ほかのスキルや規約（このリポジトリなら `.claude/rules/plugin-version-bump.md`）と役割が重ならないようにするため。
- **なぜカテゴリ順を既存ファイルに合わせるか** — 2.0.0 は推奨順を 1.1.0 の Added 始まりから、緊急度順の Security 始まりに変えた。一方で「リリース間で一貫させよ」とも言っている。既存ファイルはその順序を守り、新規ファイルだけ推奨順を使う。
- **なぜ破壊的変更を自分で探させるか** — リリースノートの不満を集めた研究では、破壊的変更は「誤って書かれる」より「書き漏れる」ことの方が多かった（[Wu et al., ICPC 2022](https://arxiv.org/abs/2203.15592)）。また、破壊的変更はメジャー版と同じくらいマイナー版やパッチ版にも含まれる（[Ochoa et al., EMSE 2022](https://arxiv.org/abs/2110.07889v1)）。コミットメッセージや版番号を信用せず、diff を確認させる。
- **なぜフラグや設定キーは名前を書いてよいか** — CLI やツールでは、フラグや設定キーそのものがユーザーインターフェースで、読み手はその名前で検索する。Kubernetes のリリースノートガイドも、影響する API・フラグ・設定を明記するよう求めている（[Adding Release Notes](https://www.k8s.dev/docs/guide/release-notes/)）。名前だけで終わらないよう、何ができるのかも書かせる。
- **なぜ移行先がないことまで書くか** — Java の非推奨 API のおよそ 3 割には、移行先の案内がなかった（[Brito et al., JSS 2018](https://bia.unibz.it/esploro/outputs/journalArticle/On-the-use-of-replacement-messages/991005773308101241)）。書かれていないと、読み手は移行先があるのか、書き忘れなのかを区別できない。
- **なぜ設定・依存・動作環境の変更も記録するか** — 読み手の役割によって欲しい情報は違う。インテグレーターは設定と依存の変更を、PM や顧客は重大な変更を重視していた（[Nath & Roy, 2022](https://ar5iv.labs.arxiv.org/html/2204.05355)）。全部を記録したうえで、カテゴリ内を影響の大きい順に並べ、誰でも上から読めば必要なものに当たるようにした。
- **なぜ書き出しと汎用的な文にこだわるか** — 読み手は見出しと行頭を拾い読みする。要約して書き直したエントリは、Issue タイトルをそのまま貼ったものより評価が高かった（[Nath & Roy, 2022](https://ar5iv.labs.arxiv.org/html/2204.05355)、[SmartNote, FSE 2025](https://arxiv.org/html/2505.17977)）。「改善した」だけのエントリは、何が変わったのかを伝えない。
- **なぜブランチへのリンクを禁止するか** — リンク切れは、リリースノートへの不満の上位に入っていた（[Wu et al., ICPC 2022](https://arxiv.org/abs/2203.15592)）。ブランチの中身は変わったり消えたりする。
- **なぜ Current state を `sh` ブロックにしたか** — 動的コンテキスト注入は、中のコマンドが非ゼロ終了するとスキル全体が起動しない。commit スキルが空リポジトリで踏んだのと同じ問題を避けるため、Claude が自分で実行する通常のコードブロックにし、さらに `|| true` で守っている。

# C# Comment

Write comments for C# code following two sources:

- **Where information goes**: t_wada's principle 「コードには How、テストコードには What、コミットログには Why、コードコメントには Why not」. Implementation-comment rules, the Why supplement and C# examples: [references/implementation-comments.md](references/implementation-comments.md).
- **How doc comments are written**: Microsoft Learn's XML documentation tags: [references/xml-doc-tags.md](references/xml-doc-tags.md).

Read both references and [references/practical-tips.md](references/practical-tips.md) (deletion, name and surprise tests; C# pitfalls) before editing. Read [references/token-saving.md](references/token-saving.md) for using the bundled Roslyn language server (`LSP` tool) and keeping context small; follow it throughout. Ask the user questions in Japanese. Write comment text in the language the file or project already uses for comments; if it has none, use English.

## Hard rules

Follow these in every step. When a step seems to conflict with one, the rule wins.

1. **Change comments only.** Do not change code, not even formatting, `using` directives, attributes (adding `[Obsolete]` is a code change) or project files. Renames, extracted methods and new tests are proposals for the report, applied only if the user already agreed in this conversation. Never add `#pragma warning disable CS1591` or `<NoWarn>` to silence missing docs.
2. **Never delete** license or copyright headers, `<auto-generated>` markers, `// ReSharper disable`/`restore`, `// NOSONAR`, `// csharpier-ignore`, the justification of a `#pragma warning disable` or `[SuppressMessage]`, or an existing `TODO`/`FIXME`. You may reword them; a vague TODO goes to the user as a question.
3. **Never invent a reason.** Every Why or Why not you write needs evidence: a commit you read (`git show`), an issue reference already in the code, or the user's answer. Carry issue IDs (`#42`, `PROJ-123`) from the evidence into the comment. No hedged reasons ("probably", "may be because") and no `// TODO: 理由を確認する`-style placeholders in the code.
4. **Document only what the code shows.** `<exception>` only for a `throw` (or `ThrowIfNull`-style guard) you can see in the body or a callee whose contract you read (or hovered), with the condition taken from that code. `null` results only for paths you can see. Write no units, ranges, defaults, complexity or thread-safety claims you cannot point to in the declaration, its body, or an existing doc; a guess becomes a question.
5. **If you cannot ask** (no `AskUserQuestion` tool, or a non-interactive run), don't stop and don't guess: leave that spot as it is and list the question in the report.

## Working efficiently

- Use Bash only for the `cs_comments.py`, `dotnet build` and `git` commands written here, exactly as written, one command per call: no shell variables, `;`, `&&`, pipes or `cd`. Other forms don't match the pre-approved tools and trigger a permission prompt. List files with Glob, search with Grep, read with Read; never `ls`, `cat`, `grep` or `find` in Bash.
- Send independent calls together in one message (all of Step 2's commands; Step 5's checks 1 and 2).
- Read only the line ranges you need (see the token reference). After an `Edit`, don't Read the file again to confirm; the tool and the language server report failures.
- Code pasted into the conversation instead of a file: skip the snapshot and the script commands, apply every other step to the pasted code, and return the result in the reply.

## Step 1: Fix the scope and take a snapshot

1. Target = `$ARGUMENTS` (a file, directory, type or member). If empty, use the `.cs` files from `git status --short`. If that is empty too, ask.
2. Resolve the target to a list of `.cs` files. Skip generated files (`*.g.cs`, `*.Designer.cs`, `*.generated.cs`, an `<auto-generated>` header, anything under `obj/`) unless named. For a type or member name, find its file with LSP `workspaceSymbol` if available, else Grep.
3. Find project settings, once: the language of existing comments, `.editorconfig`, `GenerateDocumentationFile` / `DocumentationFile` in `.csproj` or `Directory.Build.props`, StyleCop (`SA16xx` rules). If most `internal` members already have `///`, pass `--internal` to `list`.
4. Snapshot the files before any edit, and remember the printed directory:

   ```
   python3 ${CLAUDE_SKILL_DIR}/scripts/cs_comments.py snapshot <files...>
   ```

## Step 2: Inventory

Collect, without reading more than needed:

- **Existing comments and undocumented API**: `python3 ${CLAUDE_SKILL_DIR}/scripts/cs_comments.py list <files...>`. It tags each comment `DOC`, `LICENSE`, `DIRECTIVE`, `TODO`, `FIXME`, `LINE` or `BLOCK`, then prints `UNDOCUMENTED` for each `public`/`protected` declaration in a public type without a doc comment. `override` members are not listed: they take `<inheritdoc/>`.
- **Existing doc-comment problems**: `python3 ${CLAUDE_SKILL_DIR}/scripts/cs_comments.py lint <files...>`.
- **History of odd code**: for each `LINE`/`BLOCK` comment, and each spot that looks deliberate but strange, run `git log -L <start>,<end>:<file> --format=%h%n%s%n%b -n 3` and read the commit bodies. This is where Why and Why not usually are.
- **Callers and tests**, only for members whose contract is unclear from the body: LSP as in the token reference, else Grep for the name. Read two or three call sites, not all.

Then read the target members (whole file only when it is short).

## Step 3: Classify

Write a short worksheet in your reply before editing, one line per existing comment and per spot where you might add one:

```
<file>:<line> | <quote, ≤8 words> | How / What / Why / Why not / TODO / API doc / directive | delete / move to doc / keep / rewrite / write / ask | evidence (commit hash, issue, —)
```

Decide each line with this table:

| Kind | Action |
|---|---|
| **How** (restates the code) | Delete. If the code is unclear without it, add a rename or extract proposal to the report. |
| **What** on a public or protected member | Move it into the XML doc comment, then delete the `//` comment. |
| **What** elsewhere (spec of internal behavior) | Propose a test that pins it; keep the comment until the user agrees. |
| **Why** (reason for a change) | Draft it into a commit message for the report. If editing the line without knowing it would break something (a workaround for an external bug, a spec-mandated oddity), also keep it as a `//` comment. |
| **Why not** (rejected alternative, workaround, deliberate non-optimization) | Keep or write a `//` comment above the line: the alternative, the reason, when the premise stops holding, the issue ID if any. |
| **TODO / FIXME / HACK** | Keep. If it has no owner, issue ID or condition, ask for one (rule 5 if you can't). |
| **API doc** (an `UNDOCUMENTED` line, or a `DOC` comment with lint findings) | Write or fix the doc comment in Step 4. |
| `DIRECTIVE` / `LICENSE` | Keep exactly (rule 2). A directive without a reason: if the evidence gives one, write it on a `//` line above; otherwise ask. |
| Commented-out code, change history, author/date notes | Delete; version control keeps them. Commented-out code with a reason for keeping it → ask. |

Batch every question for the user into one `AskUserQuestion` call (up to 4 questions; one per spot; offer 「理由はない / 分からない」 as an option). Apply the answers before Step 4.

## Step 4: Edit

- Apply the worksheet: one `Edit` per item, top of file to bottom.
- Write a doc comment for every `UNDOCUMENTED` line and fix every lint finding, following [references/xml-doc-tags.md](references/xml-doc-tags.md). Use this shape, keeping only the parts that apply:

  ```csharp
  /// <summary>
  /// <One sentence a caller can act on; don't restate the member name.>
  /// </summary>
  /// <remarks><Side effects, blocking or expensive work, thread safety, accepted values.></remarks>
  /// <typeparam name="T"><requirements on the type argument></typeparam>
  /// <param name="name"><meaning and accepted range></param>
  /// <returns><what comes back; when it is <see langword="null"/></returns>
  /// <exception cref="ArgumentNullException"><paramref name="name"/> is <see langword="null"/>.</exception>
  ```

- `<summary>` on every documented member; `<param>` for every parameter and `<typeparam>` for every type parameter, names exactly as in the signature; `<returns>` only for non-void methods; `<value>` for a property when the value needs explaining.
- Overrides and interface implementations: `<inheritdoc/>` instead of copying the base text; add own tags only where the behavior differs.
- Document `internal`/`private` members only when the project already does or the user asks.
- Place the doc comment directly above the declaration, above its attributes.
- An `UNDOCUMENTED` member you can't describe from evidence (rule 4) → ask; don't write a summary that only restates the name.

## Step 5: Verify

Run each check, fix what your edits caused, and re-run until clean, at most 3 rounds:

1. `python3 ${CLAUDE_SKILL_DIR}/scripts/cs_comments.py check --base <snapshot dir> <files...>`: every file must print `OK`. A `CODE` line means you changed code or a string literal: undo that change. A `DIRECTIVE` or `LICENSE` line means you broke rule 2: restore that comment exactly.
2. `python3 ${CLAUDE_SKILL_DIR}/scripts/cs_comments.py lint <files...>`: no `ERROR` lines in comments you wrote or touched, and no `WARN` lines you caused. Leave pre-existing findings in comments you didn't touch for the report.
3. When a `.csproj` exists and `dotnet` is available, build once at the end: `dotnet build -p:GenerateDocumentationFile=true -v q -clp:NoSummary`. Fix every new doc-comment warning (CS1570–CS1734, see "Compiler warnings to watch" in the XML reference) for the members in scope; ignore other warnings. `cref` targets are only resolved here.
4. Re-run `list` and confirm every `UNDOCUMENTED` line in scope is gone, or listed in the report with the reason it was left.

If a command cannot run (no .NET SDK, restore fails offline), say so in the report. Never report a check you did not run as passed.

## Step 6: Report

Reply in Japanese with exactly these headings, writing 「なし」 under an empty one:

```
## 変更したコメント
### 削除(How)
### XML ドキュメントコメントへ移動・追加(What)
### 残した・書いた Why not
### TODO / FIXME
## 提案(未適用)
## コミットメッセージ案(Why)
## 確認できなかった点(質問)
## 検証結果
```

Under コミットメッセージ案, write only a subject line and a body taken from the Why evidence: no trailers (`Co-Authored-By`, session links, model names). Under each 変更したコメント heading, list `file:line` and a one-line reason. Use line numbers from the Step 2 `list` output (before editing) for changed or deleted comments, and say 「(編集前の行番号)」 once. Under 検証結果, give each Step 5 command with its outcome (e.g. `check: OK 3 files`, `lint: ERROR 0 / WARN 2 (既存)`), and whether the Roslyn language server was used. Do not commit unless the user asks.

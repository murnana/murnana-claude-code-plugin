# Practical Tips

Judgment calls and C#-specific pitfalls that the routing principle and the tag list do not settle. Read before Step 3.

## Deciding whether a comment stays

- **Deletion test**: imagine the comment gone. If a maintainer would lose nothing they need, delete it. If they would "fix" the code into a bug, it is a Why not; keep it.
- **Name test**: if the comment could become an identifier (`// timeout in seconds` → `timeoutSeconds`), rename instead. This applies only to locals, parameters of non-public members and private members. Renaming a public or protected member, or a public parameter (callers may use named arguments), is a breaking change: propose it in the report, never do it silently.
- **Surprise test**: a comment earns its place when the code would surprise a competent C# reader (an unusual ordering, a missing `await`, a catch that swallows, a `lock` on an odd object, a magic value). Mark exactly that spot.
- **Stay in scope**: change only comments on the targets. Do not reformat, translate or restyle other comments in the file; the diff should show only what was asked.

## Never touch

- Generated files: `*.g.cs`, `*.Designer.cs`, `*.generated.cs`, files with `<auto-generated>` in the header, and anything under `obj/`.
- License headers and copyright banners at the top of files.
- `#pragma warning disable CS1591` and `<NoWarn>` entries: do not add them to silence missing docs; write the docs or report the gap.
- Analyzer suppressions (`[SuppressMessage]`, `#pragma warning disable`) and their justification text, unless the user asks.

## XML doc pitfalls in C#

- **Overloads in `cref`**: `cref="Parse"` is ambiguous when overloads exist (`CS0419`). Name the overload: `cref="Parse(string, IFormatProvider)"`.
- **Type parameters**: refer to a type parameter with `<typeparamref name="T"/>`, not `cref`.
- **Keywords**: write `<see langword="null"/>`, `<see langword="true"/>`, not plain text or `<c>null</c>`, so tools render and link them consistently.
- **Do not link every type**: one `<see cref>` per type per comment, at first mention. A summary full of links reads worse in IntelliSense.
- **Nullable reference types**: the annotation already says "may be null". Document what `null` *means* ("<see langword="null"/> when the key is not found"), not that it can occur.
- **Exceptions**: document what the member throws directly (including `ArgumentNullException.ThrowIfNull` and guard clauses) and what it deliberately lets through as part of its contract. Do not list every exception a callee might theoretically throw.
- **Async**: describe the result of `Task<T>` in `<returns>` ("A task whose result is ..."). Document `OperationCanceledException` when the method honors its `CancellationToken`. Use one standard sentence for the token parameter throughout the project.
- **Records and primary constructors**: for a positional record, `<param>` tags on the record declaration document the parameters and the generated properties. For a class or struct with a primary constructor, put `<param>` tags on the type declaration.
- **Extension methods**: document the `this` parameter like any other parameter, saying what it extends.
- **Explicit interface implementations**: `<inheritdoc/>` works there too; they are easy to miss because they are not `public`.
- **Enums**: give each public member its own `<summary>`, unless the name is self-explanatory and the project leaves such members undocumented.
- **Indexers and operators**: `<param>` and `<returns>` still apply; the compiler checks them.

## Japanese comments

- Keep the project's style: です・ます or である, full-width or half-width punctuation, and whether identifiers sit inside 「」 or backticks.
- Doc comment summaries in Japanese end with 「。」 and usually take the form 「〜を取得します。」「〜かどうかを示す値を取得します。」.
- Put a space between Japanese text and inline `<c>` or `<see>` only if the project already does so.

## Working efficiently

- In a large file, finish one type at a time: list members, write docs for that type, check diagnostics, move on.
- When many members share a pattern (DTO properties, enum members), write one, check the wording with the user if the project has no precedent, then apply the same wording to the rest.
- Report a member you could not document with confidence instead of writing a vague summary such as "Gets or sets the value."

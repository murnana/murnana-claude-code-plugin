# PEP 257: Docstring Conventions

The rules of [PEP 257](https://peps.python.org/pep-0257/) (David Goodger, Guido van Rossum; Active, Informational; public domain), restated as a checklist. PEP 257 fixes the structure and wording of docstrings, not their markup. For section layout (`Args:`, `Parameters`, `:param:`), see [docstring-styles.md](docstring-styles.md).

## What a docstring is

- A string literal that is the **first statement** of a module, function, class or method. It becomes the object's `__doc__`.
- Two more kinds are not stored in `__doc__` but are read by documentation tools (Sphinx autodoc, for example):
  - **Attribute docstrings**: a string literal right after a simple assignment at the top level of a module, a class body, or `__init__`.
  - **Additional docstrings**: a string literal right after another docstring.

```python
DEFAULT_TIMEOUT = 5.0
"""Seconds to wait for the server before giving up."""
```

## Which objects need one

- Every module, normally.
- Every function and class the module exports.
- Every public method, including `__init__`.
- A package is documented in the docstring of its `__init__.py`.

## Quotes

- Always `"""triple double quotes"""`, even for one line, so the docstring can grow later without changing quotes.
- `r"""raw triple double quotes"""` when the docstring contains a backslash (regular expressions, Windows paths, LaTeX).

## One-line docstrings

For really obvious cases. They must really fit on one line.

```python
def kos_root():
    """Return the pathname of the KOS root directory."""
```

- Opening and closing quotes on the same line.
- No blank line before or after the docstring (the class exception is below).
- A phrase ending in a period.
- A command giving the effect ("Do this", "Return that"), not a description ("Returns the pathname ...").
- Not a signature. `"""function(a, b) -> list"""` is only for C functions, where introspection can't recover the parameters. The *nature of the return value* can't be introspected, though, so say it: `"""Do X and return a list."""`.

## Multi-line docstrings

```python
def complex(real=0.0, imag=0.0):
    """Form a complex number.

    Keyword arguments:
    real -- the real part (default 0.0)
    imag -- the imaginary part (default 0.0)
    """
```

- A summary line like a one-liner, then a blank line, then the elaboration. Indexing tools use the summary line, so it must fit on one line and be separated by the blank line.
- The summary may start on the line of the opening quotes or on the next line. Ruff's D212 / D213 pick one; follow the project's setting, and otherwise start on the opening line.
- The whole docstring is indented like the opening quotes.
- Unless the whole docstring fits on one line, the closing quotes go on a line by themselves.
- After the docstring of a class (one-line or multi-line), insert a blank line, so the docstring is offset from the first method.

## What to document, by kind of object

| Object | Contents |
|---|---|
| Script (stand-alone program) | Usable as its usage message (printed on bad arguments or `-h`): what it does, command-line syntax, environment variables, files. Detailed enough for a new user, and a complete quick reference to every option for an experienced one |
| Module | The exported classes, exceptions, functions and other objects, with a one-line summary each (shorter than each object's own summary line) |
| Package (`__init__.py`) | As for a module, plus the modules and subpackages it exports |
| Function or method | Behavior; arguments; return value(s); side effects; exceptions raised; restrictions on when it may be called. Each only if applicable. Mark optional arguments. Say whether keyword arguments are part of the interface |
| Class | Behavior; public methods; instance variables. If it is meant to be subclassed and has an extra interface for subclasses, list that separately. Document the constructor in `__init__`'s docstring. Each method documents itself |
| Subclass | If most behavior is inherited, say so and summarize the differences. "Override": the method replaces the parent's and doesn't call it. "Extend": the method calls the parent's and adds behavior |

## Wording

- Use the real argument names in running text, never the upper-case Emacs convention (`TIMEOUT`). Python is case-sensitive, and the names double as keyword arguments.
- List each argument on its own line.

## Indentation handling

Docstring tools (`inspect.cleandoc`, `help()`, Sphinx) normalize indentation like this:

- Indentation on the first line (up to the first newline) is insignificant and removed.
- From the second line on, they strip the smallest indentation found among the non-blank lines. Relative indentation, as in code examples and nested lists, is kept.
- Blank lines at the beginning and the end are removed.

So these two are equivalent after processing, and neither needs manual alignment:

```python
def foo():
    """A multi-line
    docstring.
    """

def bar():
    """
    A multi-line
    docstring.
    """
```
